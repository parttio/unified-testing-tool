# 0.1.0-alpha6

Sixth alpha of the Unified API for Vaadin UI tests. It brings responsive testing: in a browser, every test runs at an
exact Viewport that a test or a run can set, layout assertions and automatic layout checks find what scrolls
sideways, is clipped or overlaps, the Findable View and the failures say when a user can't reach a component, and a
Viewport Comparison puts the runs at each Viewport side by side. The Core Set grows with the components a responsive
application navigates with: app layout, menu bar overflow and side navigation. The Migration Recipes convert them,
and the resizes of TestBench and Dramafinder tests.

The API can still change between alphas. **The accessible name is now the browser's** on every Testing Tool, under
**Breaking changes**: a `withAccessibleName(..)` that matched a plain component by its text becomes `withText(..)`.
Otherwise a run behaves differently in the ways under **Changed behaviour**: on Selenium a click on a covered
component fails as on Playwright, and what a Testing Tool can't do fails at once instead of after the timeout. A
custom adapter keeps compiling; one built on the older `ElementFacts` constructors reports no ids, so the Findable
View doesn't suggest `withId(..)` for its components.

## Get it

On Maven Central as `org.vaadin.addons:*:0.1.0-alpha6`. Import `unified-test-bom` and add the adapters you
run on as test dependencies (see [Try it](https://parttio.github.io/unified-testing-tool/#try-it)).

Requires Java 21, Vaadin 25.3 and, for `@UnifiedSpringBootTest`, Spring Boot 4.1. The Playwright adapter uses
Dramafinder 2.2.4. An exact Viewport on Selenium with Firefox needs Firefox 132 or later.

## Breaking changes

- **The accessible name is the browser's, on every Testing Tool**
  ([#641](https://github.com/parttio/unified-testing-tool/issues/641)): `withAccessibleName(..)`,
  `UnifiedElement.getAccessibleName()`, the Findable View, Near Misses and Step Targets compute it as browsers and
  Dramafinder's `getAccessibleName()` do: the `aria-labelledby` targets' texts (every id, joined with a space), else
  `aria-label`, else a field's label, `setAriaLabel(..)` or `setAriaLabelledBy(..)`, else the own text of a component
  named by its content (a button, tab, menu item, breadcrumb item, badge, notification, link or heading, without its
  icon or tooltip). Anything else has no name: `getAccessibleName()` returns `null` where it returned the text. On
  Playwright the name is read with Dramafinder's `AccessibleNames`. See
  [4. Locating](../spec/04-locating.md#filters) and [ADR 0016](../adr/0016-accessible-name-follows-the-browser.md).
  - **Migration:** `withAccessibleName("…")` on a `Div`, a `Span` or another component that only matched by its
    text becomes `withText("…")`. Where a component has both `aria-label` and `aria-labelledby`, the expected name is
    the `aria-labelledby` text. A select's name includes the value it shows (`"Plan Pro"`). A Grid named with
    `setAriaLabel(..)` has no name a lookup finds: give it a test id.

## New

- **Exact Viewports** ([#489](https://github.com/parttio/unified-testing-tool/issues/489),
  [ADR 0011](../adr/0011-responsive-testing-viewports-layout-findings-viewport-comparison.md)): in a browser, every
  test runs at an exact Viewport, 1280 × 720 by default. `@Viewport(width = 375, height = 667, name = "phone")` on a
  test or its class sets the size it starts at, and implies `@RequiresBrowser`. `page.setViewport(768, 1024)` changes
  it during the test, as often as needed, and waits until the application has heard of the new size; `page.viewport()`
  gives the current one. Windows from `openWindow()` and `openAsUser()` start at the test's Viewport. Playwright sets
  it with `setViewportSize`, Selenium with WebDriver BiDi `browsingContext.setViewport` on Chrome and Firefox 132 or
  later, per tab ([#490](https://github.com/parttio/unified-testing-tool/issues/490)); an older Firefox refuses with
  its version, so a test that needs its Viewport is skipped and the others run with a warning. The reports name the
  Viewport each test ran at. See [Viewports](../guide/configuration.md#viewports).

- **Layout assertions** ([#491](https://github.com/parttio/unified-testing-tool/issues/491)): in a browser,
  `assertThat(page).hasNoHorizontalScroll()` (neither the page nor a container in it, such as AppLayout's content area,
  scrolls sideways; Grid, Tabs, TabSheet and VirtualList scroll by design), `assertThat(page).hasNoLayoutFindings()`
  (nothing scrolls sideways, no component is clipped out of reach, no component a user acts on overlaps another),
  `assertThat(wrapper).isInViewport()` and `isNotClipped()`. Each measures the page in one round trip with the same
  script on Playwright and Selenium, waits for AppLayout's drawer to finish sliding, and retries until the timeout.
  `page.checkLayout()` measures at any moment, as a User Step. See [Layout](../guide/assertions-and-waiting.md#layout).

- **App layout and menu bar overflow** ([#493](https://github.com/parttio/unified-testing-tool/issues/493)):
  `page.find(UnifiedAppLayout.class)` finds an `AppLayout`; `assertThat(layout).isOverlay()`, `isNotOverlay()`,
  `isDrawerOpened()`, `isDrawerClosed()`, and `openDrawer()`, `closeDrawer()`, `toggleDrawer()` with its DrawerToggle,
  as a user does. `assertThat(menuBar).hasOverflowItems("Share", "Print")` and `hasNoOverflowItems()` check which items
  a narrow menu bar has moved into "More options"; `clickItem(..)` on one of them fails, pointing to
  `unfoldingOverflow().clickItem(..)`, which opens that menu first ([#664](https://github.com/parttio/unified-testing-tool/issues/664)). Overlay and overflow are
  browser only. The Findable View lists the layout with `(overlay)` and `(drawer closed)`. See
  [App layout](../guide/components.md#app-layout).

- **Reach in the Findable View and in failures** ([#494](https://github.com/parttio/unified-testing-tool/issues/494)):
  in a browser, the Findable View's header names the Viewport, and a line says when a user can't get to its component
  as it shows: `(clipped)`, `(behind the AppLayout drawer)`, `(behind button “Menu”)`, `(hidden in the AppLayout
  drawer)` or `(hidden in the MenuBar overflow)`. An action on a component something covers or clips fails with that
  in `Found`, the same on Playwright and Selenium: `Expected a reachable button with text “Save”`, `Found behind the
  AppLayout drawer`. See [Reports and failures](../guide/reports-and-failures.md).

- **Viewport Comparison** ([#495](https://github.com/parttio/unified-testing-tool/issues/495)): run the same tests
  once per Viewport (`vaadin.testing.viewport`) with the layout checks on, then `CompareRuns` compares each run with
  the widest, measurement point by measurement point. It writes `viewport-comparison.html` (a matrix of scenarios
  against Viewports, with each cell's screenshots side by side, its Layout Findings and the components it loses), a
  `.json` for agents and a Markdown summary for the GitHub job summary. Components hidden in the AppLayout drawer or
  the MenuBar overflow are explained; the others need review. It reports and fails nothing. `CompareRuns --out <dir>`
  sets where. See [A weekly responsive run](../guide/ci-setup.md#a-weekly-responsive-run-comparing-viewports).

- **The Findable View suggests `withId(..)`** ([#609](https://github.com/parttio/unified-testing-tool/issues/609)):
  a component that has an id gets `withId("…")` when nothing else of its own singles it out, and inside a Template
  (entered with `findTemplate` or a `TemplateScope` Wrapper) the id comes first, as it is the lookup that works there
  on every Testing Tool. On Browserless, a Template's `@Id` button whose text the template writes now reads
  `button (no name; id “save”)  find(UnifiedButton.class).withId("save")` instead of `not unique: 5 alike`. Flow's
  `ROOT-…` id is never suggested. A custom adapter fills the id in with the new `ElementFacts` constructor; the
  older ones report none. The guide and spec 04 now also say that a Template's `element()` is its host, whose
  `findDescendants(..)` stays in the light DOM ([Templates](../spec/04-locating.md#templates)).

- **Check a path the test only partly knows** ([#610](https://github.com/parttio/unified-testing-tool/issues/610)):
  `assertThat(page).hasPathMatching("products/\\d+")` passes when the page's path matches the regular expression as
  a whole, without a leading `/` and the query string, such as after opening an item whose id the test doesn't
  know. It retries until the timeout like `hasPath(..)`, on every Testing Tool, and reads `see path matching
  “products/\d+”` in the User Steps. A `java.util.regex.Pattern` overload takes flags. See
  [3. Navigation](../spec/03-navigation.md) and [ADR 0017](../adr/0017-the-page-path-is-checked-not-read.md).

- **Grid cell by index** ([#614](https://github.com/parttio/unified-testing-tool/issues/614)):
  `row.cell(2)` is the Scope of the row's cell in the column at index 2 among the visible columns, as
  `getCellText(2)` counts them, for components in a column without header text, such as an action button:
  `row.cell(2).find(UnifiedButton.class).withText("Edit").click()`. The User Steps name it `cell at index 2`.

- **A Template's lookup names its class before the test uses it**
  ([#616](https://github.com/parttio/unified-testing-tool/issues/616)): the Findable View and the Near Misses now
  print `page.findTemplate(SearchBar.class)` for a `<search-bar>` Template from the first failure, instead of
  `findTemplate(<the class with @Tag("search-bar")>.class)`. The class is the only one in the application's packages
  that declares the tag. Those packages are the test's package, the `@SpringBootApplication`'s, the
  `vaadin.testing.browserless.view-packages` and the opened routes' packages, and they're scanned the first time a
  tag needs a class. The lookup is the same on every Testing Tool. When no class there declares the tag, or several
  do, the placeholder stays. `unified-test-api` now depends on ClassGraph, which Browserless Test already brings
  ([ADR 0018](../adr/0018-template-class-from-the-application-packages.md)).

- **Side navigation** ([#658](https://github.com/parttio/unified-testing-tool/issues/658)):
  `page.find(UnifiedSideNavItem.class).withLabel("Orders").click()` clicks an item of a `SideNav` as a user does,
  following its path as a link and waiting for the new page; a nested item is found inside its parent item or its
  `UnifiedSideNav`, and its collapsed parents are expanded first. `expand()`, `collapse()`, `getPath()`, `getItems()`
  and `assertThat(item).isCurrent()`, `isExpanded()`, `hasPath(..)`, `hasItems(..)`. The Findable View lists side
  navs and their items, with `(current)` and `(collapsed)`. On Browserless, an item is current and expanded as the web
  component makes it in a browser. See [Side navigation](../guide/components.md#side-navigation).

## Changed behaviour

- **Dramafinder 2.2.3** ([#448](https://github.com/parttio/unified-testing-tool/issues/448)): `unified-test-bom`
  manages Dramafinder 2.2.3 (was 2.2.2).
  - **Waiting after an action is Dramafinder's own wait on Playwright.** Since 2.2.3 that wait also covers a page
    load the action started (`Page.setLocation(..)`, a link to another document, a form post), and Flow starting the
    new page's UI ([parttio/dramafinder#320](https://github.com/parttio/dramafinder/issues/320)). The adapter's own
    navigation, page-load and idle scripts are gone. Its 5-second idle window before Dramafinder's 30-second wait is
    gone with them; the wait before an action ([ADR 0014](../adr/0014-playwright-actions-wait-for-flow-idle-before-acting.md))
    keeps its 5-second cap.
  - **Selecting an already selected item of a `MultiSelectComboBox` keeps it selected on Playwright.** It used to
    toggle the item off, and the select then failed, unlike on the other Testing Tools
    ([parttio/dramafinder#321](https://github.com/parttio/dramafinder/issues/321)).

- **On Selenium, clicking a component something covers fails** ([#494](https://github.com/parttio/unified-testing-tool/issues/494)):
  TestBench clicks with a script, which reached a button under the AppLayout drawer or a dialog's backdrop, where a
  user couldn't. The click now checks what is under its point first and fails, as on Playwright, saying what covers
  the component. One round trip fewer per click as well.

- **Grid: markup a renderer draws, and row clicks** ([#608](https://github.com/parttio/unified-testing-tool/issues/608)):
  a `LitRenderer`'s markup in a cell, such as Crud's `vaadin-crud-edit` pencil or a clickable card, is found in a
  browser with a Wrapper bound to its tag, `row.cell(1).find(UnifiedCrudEdit.class).click()`. On Browserless, a
  lookup in such a cell now fails, naming `@RequiresBrowser` and the Escape Hatch to
  `GridTester.invokeLitRendererFunction`, instead of `Target column doesn't have a ComponentRenderer`. On Selenium,
  `row.click()` and `row.doubleClick()` now click a spot of the row free of interactive content, as on Playwright,
  rather than the first cell's content; a row that such content covers fails with the same message on both,
  naming `row.cell(..).find(..).click()`. See [ADR 0015](../adr/0015-renderer-markup-is-found-by-tag-wrappers-row-click-avoids-it.md).

- **What a Testing Tool can't do fails at once, and every failure names its error**
  ([#611](https://github.com/parttio/unified-testing-tool/issues/611)): a lookup, action, assertion or `waitUntil(..)`
  whose attempt throws `UnsupportedOperationException`, such as a lookup inside a LitRenderer's cell on Browserless,
  fails at the first attempt instead of after the timeout. Other errors are still retried until the timeout. The
  failure names the error its last attempt threw in a new `Cause` line (`Cause  UnsupportedOperationException: …`),
  and `user-steps.json` has it as `failure.cause`. The Findable View ends with `Not listed: link (…)` for a kind whose
  lookup threw, instead of leaving it out. The same on every Testing Tool
  ([ADR 0019](../adr/0019-only-what-a-testing-tool-cannot-do-ends-a-wait-early.md)).

- **Several matches name the hidden ones** ([#619](https://github.com/parttio/unified-testing-tool/issues/619)): when
  a lookup matches several components, the failure's `Found` line marks each listed match that is not visible
  `(hidden)`, as Near Misses and the Findable View already do: `Found 2: button “Cancel”, button “Cancel” (hidden)`.
  Add `.visible()` to single out the one the user sees. The same on every Testing Tool.

- **A grid row or column as text** ([#620](https://github.com/parttio/unified-testing-tool/issues/620)): a row's
  and a column's `toString()` read as the target of their User Steps, `row where Name is “Unique cake” in grid`
  or `column “Name” in grid`, instead of code (`row().withCellText("Name", "Unique cake")`), so that
  `page.step("Edit " + row, ..)` names the User Task in the reports' words. It asks the grid nothing. Failure
  messages and `grid.describe()` still show the code that finds the row.

- **No `@WithMockUser` advice in a test that checks the login** ([#622](https://github.com/parttio/unified-testing-tool/issues/622)):
  the TestBench recipe's "signs in through the login form: ... consider @WithMockUser" Migration Marker is left out
  of a test method that asserts on a call to a login element, such as
  `assertEquals("Email", loginView.getUsernameLabel())`. Such a test checks the login itself. Every other call on a
  login element is still marked, as before.

- **Dramafinder 2.2.4** ([#666](https://github.com/parttio/unified-testing-tool/issues/666)): `unified-test-bom`
  manages Dramafinder 2.2.4 (was 2.2.3). On Playwright, `UnifiedMenuBar` reads its items, and the items folded into
  "More options", through Dramafinder's `MenuBarElement`, and `unfoldingOverflow()` opens that menu with Dramafinder's
  ([parttio/dramafinder#334](https://github.com/parttio/dramafinder/issues/334)); the adapter's own menu bar script is
  gone. Nothing changes in what the tests see. A project's own Dramafinder code left behind the Escape Hatch now gets
  `MenuBarElement.getItemLabels()` without "More options".

## New settings

- **`vaadin.testing.viewport`** ([#489](https://github.com/parttio/unified-testing-tool/issues/489)): the Viewport
  of every test without `@Viewport`, `[name:]WIDTHxHEIGHT` such as `phone:375x667`; `1280x720` by default. A run
  whose Testing Tool can't set it exactly skips its tests with the reason, so a run at a size never compares the
  wrong one. See [Configuration](../guide/configuration.md).

- **Automatic layout checks** ([#492](https://github.com/parttio/unified-testing-tool/issues/492)):
  `vaadin.testing.layout-checks=on` measures the layout after every navigation, reload and `setViewport`, in a
  browser, and shows each **Layout Finding** in amber under the User Step that measured it, in `report.html` and
  `user-steps.json`. `vaadin.testing.layout-findings=fail` makes that step fail; `report` (the default) only reports.
  `vaadin.testing.layout-checks.screenshots=on` keeps a screenshot per measurement, with the finding's box on it. Off
  by default: nothing is measured, no extra round trip. See [Layout](../guide/assertions-and-waiting.md#layout).

## Fixed

- **Links beside plain text on Browserless** ([#603](https://github.com/parttio/unified-testing-tool/issues/603)):
  `page.find(UnifiedLink.class)`, and any Wrapper declared `@UnifiedComponent(value = Component.class, tag = "…")`,
  no longer throws `UnsupportedOperationException` on a page that holds a Flow `Text` component, such as the text
  `add(String)` makes. The text is never a match, and the Findable View lists the page's links again.

- **Actions wait for a round trip already under way, on Playwright** ([#604](https://github.com/parttio/unified-testing-tool/issues/604)):
  after an Escape Hatch click (a Playwright `Locator.click()` returns before the server answers), the next Unified
  action acted at once, and the server's late answer could overwrite what it typed. Auto-Wait now also waits, before
  acting, until Flow is idle, for at most 5 s, then acts anyway, so an app that stays busy (`@Poll`, a long request)
  can still be driven. It shares the call that checks the component is usable, so the round trips per action of the
  Performance Pairs don't change.
  TestBench and Browserless already behaved this way. See [5. Waiting](../spec/05-waiting.md#auto-wait) and
  [ADR 0014](../adr/0014-playwright-actions-wait-for-flow-idle-before-acting.md).

- **A password inside the user name no longer garbles the reports**
  ([#605](https://github.com/parttio/unified-testing-tool/issues/605),
  [ADR 0014](../adr/0014-secrets-are-masked-as-substrings-except-the-login-user-name-and-display-name.md)):
  `login("barista@vaadin.com", "barista")` read `sign in as “••••@vaadin.com”`, and a `@DisplayName` like "A
  signed-in barista logs out" read "A signed-in •••• logs out". A login's password is no longer masked inside that
  login's own user name (unless the two are equal), and the scenario name the author wrote (`@DisplayName`, or the
  method's name) is shown as written. The password stays masked everywhere else, even inside a longer word, and a
  parameterized or repeated invocation's name is still masked.

- **Page objects of an application under `com.vaadin.*`** ([#606](https://github.com/parttio/unified-testing-tool/issues/606)):
  a `TestBenchElement` subclass is TestBench's own only in `com.vaadin.testbench.*` or a component's
  `com.vaadin.flow.component.**.testbench` package, so the page objects of an application such as Bakery
  (`com.vaadin.starter.bakery`) are custom elements: the dry run lists them and reports their classes `migrates partly`,
  each statement calling one gets the `TestBench page object: ...` Migration Marker, a `$(X.class)` lookup of one says
  it is a custom element, and the tests reaching one get `@RequiresTestingTool(SELENIUM)`. A statement calling a page
  object gets its marker even when it already has another one, such as the sign-in marker.

- **Navigation the TestBench recipe can't convert is marked** ([#607](https://github.com/parttio/unified-testing-tool/issues/607)):
  every `get(..)` on a `WebDriver` that the recipe keeps gets a Migration Marker suggesting `page.navigate("<path>")`,
  whatever the URL's form: a helper's parameter (`driver.get(url)`), a local, a method call or a field. In a class
  that becomes a `@UnifiedSpringBootTest`, a field holding a local application URL with a fixed port, such as
  `APP_URL = "http://localhost:8080/"`, gets one too. Such a navigation used to stay unmarked and kept testing the
  server the build starts, not the app the test starts on a random port.
- **`testBench` declared when a test passes the driver to a plain method** ([#607](https://github.com/parttio/unified-testing-tool/issues/607)):
  a TestBench test calling `open(getDriver(), url)`, where `open` makes no TestBench call, now declares the
  `TestBenchEscapeHatch testBench` its migrated `open(testBench.getDriver(), url)` reads, so it compiles.

- **`getRunLocallyBrowser()` in migrated TestBench tests** ([#621](https://github.com/parttio/unified-testing-tool/issues/621)):
  `TestBenchEscapeHatch` has `getRunLocallyBrowser()` and `getRunLocallyBrowserVersion()`, so a TestBench test
  calling them, such as `if (getRunLocallyBrowser() == null)`, compiles after the migration. The browser is the one
  `vaadin.testing.selenium.browser` sets (`CHROME` or `FIREFOX`), or `null` without the setting, as for a TestBench
  test without `@RunLocally`; the version is always `""`, any version.

- **Menu bar items and subclasses with their own tag** ([#656](https://github.com/parttio/unified-testing-tool/issues/656),
  [#493](https://github.com/parttio/unified-testing-tool/issues/493)): on Playwright,
  `page.findComponent(DrawerToggle.class)` found the page's buttons, since `DrawerToggle` extends `Button`; a component
  class with a tag of its own is now found by that tag. `UnifiedMenuBar.getItems()` is the same on Playwright and
  Selenium when items overflow: every top-level item, never the "More options" button.

- **Findable View** ([#658](https://github.com/parttio/unified-testing-tool/issues/658)): a component that isn't
  unique is printed with the lookup through a dialog or another container only when the container holds that very
  component. Before, the profile's own Email field was printed as "one in dialog “Change email”" while a dialog held
  another Email field. A component named by a Wrapper's own filter, such as a side nav item's `withLabel(..)`, is now
  told apart by its container too.

## Migration

- **Viewport and window sizes** ([#496](https://github.com/parttio/unified-testing-tool/issues/496)): the TestBench and
  Dramafinder Migration Recipes convert resizes. The size a test starts at, a `resizeViewPortTo(w, h)` or
  `setViewportSize(w, h)` first in a `@BeforeEach` or a test, becomes `@Viewport(width = w, height = h)`, and a later
  one `page.setViewport(w, h)`; `window().getSize()` and `viewportSize()` read `page.viewport()`. A window size,
  `maximize()`, a driver's `--window-size` and a copied `SpringPlaywrightIT` that opens its pages at a size get a
  Migration Marker. See [the mapping](../spec/appendix-mapping.md#viewport-and-window-sizes-the-migration-recipes-convert).

- **Failsafe profiles that tested something else are marked** ([#613](https://github.com/parttio/unified-testing-tool/issues/613)):
  the TestBench recipe leaves a Migration Marker, an XML comment, on a pom profile whose Failsafe run tested a server
  or browser outside the test: one that starts the app as a native executable, with `exec` or another
  `spring-boot` goal than `start`/`stop`, one that gives Failsafe a server address, and one with TestBench grid
  (`com.vaadin.testbench.Parameters.gridBrowsers`, `hubHostname`) or Sauce Labs settings. Such a profile used to run
  green after the migration against the JVM app the test starts, on a local browser, with nothing saying so. The
  recipe changes nothing else in the profile ([ADR 0020](../adr/0020-failsafe-profiles-that-test-elsewhere-get-a-marker-no-remote-grid.md)).
  The Selenium adapter has no remote Selenium grid; the configuration guide and [2. Test setup](../spec/02-test-setup.md)
  now say so, and remote-grid support is on the roadmap ([#645](https://github.com/parttio/unified-testing-tool/issues/645)).

- **TestBench removed once the Migration Markers are resolved** ([#623](https://github.com/parttio/unified-testing-tool/issues/623)):
  the `resolve-migration-markers` skill ends with a step that, when no test source still uses TestBench (a
  `com.vaadin.testbench.*` or `*.testbench.*` class, or `TestBenchEscapeHatch`, the rule of `RemoveTestBenchWhenUnused`),
  removes the direct `vaadin-testbench-*` dependencies, compiles and runs the suite again, puts them back if that fails,
  and names what it removed in its report. Before, TestBench stayed in the pom after the skill had converted the last
  page object.

- **App layout** ([#669](https://github.com/parttio/unified-testing-tool/issues/669)): the Migration Recipes convert
  TestBench's `AppLayoutElement` and `DrawerToggleElement` and Dramafinder's `AppLayoutElement` to
  `page.find(UnifiedAppLayout.class)`: `isDrawerOpened()`, `openDrawer()`, `closeDrawer()`, `toggleDrawer()`,
  `assertThat(layout).isDrawerOpened()` / `isDrawerClosed()`, and `isOverlay()` / `assertThat(layout).isOverlay()`,
  which add `@RequiresBrowser` to the test. TestBench's `setDrawerOpened(true)` becomes `openDrawer()` with a
  Migration Marker, as TestBench set the property and the Unified API clicks the DrawerToggle as a user does;
  `getDrawerToggle().click()` becomes `toggleDrawer()`. See
  [App layout the Migration Recipes convert](../spec/appendix-mapping.md#app-layout-the-migration-recipes-convert).

## Known limitations

- **Responsive testing needs a real browser** ([ADR 0011](../adr/0011-responsive-testing-viewports-layout-findings-viewport-comparison.md)):
  Browserless lays nothing out, so a test with `@Viewport` is skipped there, the layout assertions and
  `isOverlay()`, `hasOverflowItems(..)` ask for `@RequiresBrowser`, and the layout checks measure nothing.
- **Selenium on Firefox needs Firefox 132 or later** for an exact Viewport
  ([#490](https://github.com/parttio/unified-testing-tool/issues/490)); an older one skips the tests that need it.
- **Only the Viewport is emulated**, not the device: `screen.width`, touch input and the device pixel ratio are the
  browser's own.
- **The Viewport Comparison reports and fails nothing**, and matches measurement points by order until two runs take
  different User Steps ([#495](https://github.com/parttio/unified-testing-tool/issues/495)).
- **A Dramafinder test whose copied `SpringPlaywrightIT` opens its pages at a size is not migrated**, as for any
  `setupTest()` override; its Migration Marker names the `@Viewport` to keep
  ([#496](https://github.com/parttio/unified-testing-tool/issues/496)).
