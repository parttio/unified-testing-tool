# Agent testing tools since 2026-11-17: what changed, and what it means for the Unified API

Research for [#503](https://github.com/parttio/unified-testing-tool/issues/503), part of the roadmap map [#499](https://github.com/parttio/unified-testing-tool/issues/499). It updates [agentic-testing-environment-roadmap.md](agentic-testing-environment-roadmap.md) (sources N1–N23, candidates C1–C17, "Not verified") and §3 of [web-framework-testing-landscape.md](web-framework-testing-landscape.md) (AI1–AI23, AG1–AG14). It doesn't repeat them.

**Question.** What changed in testing with coding agents since the roadmap note was researched on 2026-11-17? For each change: does it make a roadmap candidate redundant, more urgent, or easier to build? Which new candidates does it suggest? Also: what could the earlier note not read?

**Method.** Every source was read on **2026-11-22**. GitHub sources were read from shallow clones at the commit given in [Sources](#sources), using their commit logs for 2026-11-16 to 2026-11-22. Each change was then followed to the file it touched. Web pages were read live and are not pinned. Two scopes are used:

- **New**: a change dated 2026-11-17 or later.
- **Missed**: a change dated earlier that neither note recorded, or recorded wrongly. The earlier notes pinned some sources (`vaadin/docs@f0394e7`, `playwright-mcp@78eca85`) and missed what had landed elsewhere.

Labels: a **fact** has a source. **[opinion]** marks this note's reasoning. Glossary terms (Unified UI Test, Testing Tool, Findable View, User Step, Base Run, Migration Recipe, Escape Hatch…) are used as [GLOSSARY.md](../../GLOSSARY.md) defines them.

**Scope note.** Several C-candidates shipped between 2026-11-17 and today. Examples are the Findable View (`docs/guide/finding-components.md`), `CompareRuns` and "Compared with another Testing Tool" (`docs/guide/ci-setup.md`), `summary.json`, and `llms.txt` (`docs/guide/for-agents.md`). Which ones shipped, and how much of each, is [#500](https://github.com/parttio/unified-testing-tool/issues/500)'s question. This note reads each candidate as it stands on `main@39411f6`.

## Answer in short

1. **The biggest change is Vaadin's own, and it overlaps this project.** Vaadin Skills 0.3.0 ships `vaadin-browserless-testing` (M1). It is an agent skill that writes Browserless Tests as use cases, with actors and page objects, finds components by label, text or accessible name, runs the tests until they pass, and "never weaken[s] the story". It does the same job as this project's `write-unified-ui-tests` skill on one Testing Tool, and Vaadin's docs and MCP server back it. A project with both installed has two skills that both match "write tests for this view". Nothing measures what happens then. The Unified API still has things this skill does not: it runs on a browser too, keeps User Steps, Near Misses and `Did you mean`, and has a scored skill.
2. **The browser-agent tools moved little in these five days.** Playwright released nothing new (1.65.1 is still the latest; test agents are still JS-only). Playwright MCP 0.0.86 and `playwright-cli` 0.1.25 only roll the Playwright version. Chrome DevTools MCP, Stagehand, Browser Use and Cypress shipped fixes and small additions. None changes a candidate's verdict.
3. **One protocol shift, which the earlier notes missed: pages now expose tools to agents.** Chrome DevTools MCP lets a page register "third-party developer tools" (internal state, component hierarchies) that the agent can call (M7). WebMCP (`navigator.modelContext`), which Playwright 1.64 already supports (landscape AG14), is now an experimental category in Chrome DevTools MCP too. A Vaadin application in development mode could expose its server-side component tree, or the Findable View, to any browser agent through these hooks. That makes C4 (live session) easier to start and gives it a second shape.
4. **The agent-tool makers now measure their formats.** WebdriverIO MCP changed its element output to "accessibility tree, one ref and best selector per actionable line". The commit says a small model then picked a correct selector in 51 of 56 tasks instead of 43 (M8). Storybook MCP added `stories-changed` and `review-create` (M9). Both are precedents for things this project plans or has built: a Findable View measured by an eval, and test selection plus a review page.
5. **What the earlier note couldn't read is now partly read.** `playwright-mutation-gate` inverts one marked assertion per test and fails CI if the test stays green (M12). That is prior art for C3's level 1½, and it shows C3 level 2 (step-skip reruns) is still unshipped elsewhere. Applitools ships an MCP server for visual-test review (M13), Octomind one for test creation and runs (M14), and Mabl a `mabl agent debug` command (M15). Mutta is a 2024 research tool for E2E mutation testing; only its bibliographic record was reachable. Testim showed no agent feature in what was readable.

**Effect on the roadmap** [opinion]: **more urgent**: C12 (eval fixtures), now in a form that also covers skill collisions; C3 (weak-test checks); C9 (accessibility on Browserless). **Easier**: C4 (through page-exposed tools), C11 (Storybook's precedent), C6 (Playwright 1.65's `normalize()` Java string for migrations). **Redundant**: none. C17 ("Vaadin MCP and Skills know the Unified API") changes from "ask Vaadin" to "coexist with Vaadin's testing skill". New candidates: [T1–T6](#new-candidates).

### Inferences

- **Vaadin is drawing the same line this project drew, from the other side** [opinion]. Its skill makes Browserless the inner loop and says browser tests are a thin layer (M1). The Unified API's default Testing Tool is Browserless and the same test also runs in a browser (roadmap H1). The two agree on what to test first. They differ in what they hand the agent: Vaadin's skill writes `window.findButton().withText(..)` against one Testing Tool. The Unified skill writes Wrappers that also run on Playwright and Selenium, and every run leaves User Steps and a Findable View.
- **"Decide who is wrong, never weaken the test" is now the standard rule**, in Vaadin's skill (M1), this project's skill (roadmap H12) and Playwright's healer (landscape AI1). Each of them asks the agent to follow it; none checks it. C3 (does the test fail when the feature is broken) and C12 (an eval fixture where the application is wrong) are still the only checks proposed for it. `playwright-mutation-gate` (M12) is the one tool found that checks part of it, and it needs a person to mark each assertion first.
- **The page is becoming an MCP server** [opinion]. WebMCP (landscape AG14) and Chrome DevTools' third-party tools (M7) let the application under test hand tools and state to whichever browser agent the developer uses. For a Vaadin application, the state worth handing over is on the server, the component tree. Until now, C4 assumed a new CLI was needed to show an agent that tree.
- **Output formats for agents are being measured** (M8, and this project's H13). The Findable View has no such number yet.

## 2. What each change means for the roadmap candidates

"More urgent", "easier" and "redundant" are this note's reading [opinion]. C1–C17 are the roadmap note's.

| Change | Candidate | Effect | Why |
|---|---|---|---|
| M1 Vaadin's browserless testing skill | **C17** (Vaadin MCP and Skills know the Unified API) | **changes shape, more urgent** | Vaadin now has its own test-writing skill. The question is no longer "teach Vaadin's MCP about the Unified API" but "what happens when both skills are installed". A test written by `vaadin-browserless-testing` in a Unified project is a Direct Test: it doesn't run on Playwright and leaves no User Steps. See T1. |
| M1 | **C12** ("the application is wrong" eval fixtures) | **more urgent** | Vaadin's skill states the same rule ("decide which before changing anything") with no measurement. A fixture set that scores it would show the Unified skill's measured advantage, and could score both skills on the same prose scenarios. |
| M1 | Migration Recipes (H14) | **easier to justify** | New Browserless Tests written by Vaadin's skill will use the 25.2 contexts API and locators. ADR 0005 already converts "the Locators mixin … like the context API's locators". Each project that adopts Vaadin's skill is a future input for the Browserless Migration Recipe. |
| M1 (console check) | **C5** (server logs and console per User Step, smoke check) | **more urgent** | Vaadin's skill tells agents to add browser smoke tests that check "the browser console shows no errors", but neither Browserless Test nor the Unified API offers such a check. `assertThat(page).hasNoErrors()` on every Testing Tool fills that gap. |
| M2 `vaadin-usage-review` | none | — | It reviews application code, not tests. It could run on the views a Unified UI Test touches, but that is the user's choice. |
| M3 Vaadin documents Playwright and Dramafinder | the Playwright Testing Tool | **more users** [opinion] | Vaadin's docs now send Playwright users to Dramafinder, the Unified API's Playwright Testing Tool. More users arrive with Direct Tests on Dramafinder, so the Dramafinder Migration Recipe matters more. |
| M5 Copilot accessibility checker | **C9** (accessibility checks) | neutral | Interactive and in the IDE, not in a test run. C9's Browserless subset is still unique. |
| M6 Dramafinder `ViewOutline` | **C1** (Findable View) | **precedent, not redundant** | Dramafinder already printed verified lookups for one Testing Tool, from a live browser page. The Findable View does the same on every Testing Tool, in User Step words. The two formats should be compared, and C1 should credit `ViewOutline` as prior art. The roadmap's "None found prints a typed lookup…" was wrong for Dramafinder alone. |
| M6 Dramafinder 2.2.x | [#448](https://github.com/parttio/unified-testing-tool/issues/448) | **easier** | The releases contain the "tool-adapter APIs" the Playwright adapter's workarounds wait for. |
| M7 page-registered tools (Chrome DevTools MCP, WebMCP) | **C4** (live session) | **easier; second shape** | Instead of starting with a CLI daemon, a development-mode hook in the application (or a test-scope dependency) registers a `devtoolstooldiscovery` tool group: `describe` (the Findable View), `steps` (the User Steps so far), `lookup` (resolve a Unified lookup). Any agent with Chrome DevTools MCP gets Unified-term context about the page it already drives. This works only in a browser and needs no new CLI. See T2. |
| M7 `lighthouse_audit` (accessibility and "agentic browsing") | **C9** | slightly less urgent in a browser | An agent already gets accessibility findings from Chrome DevTools MCP. The browser half of C9 adds little beyond making them a test assertion. The Browserless half is unchanged. |
| M8 WebdriverIO's measured element format | **C1**, **C12** | **easier to evaluate** | WebdriverIO shows how: the same tasks, two output formats, the rate of correct selectors. The writing-skill harness (H13) could score "agent with the Findable View" against "agent reading the view source" in the same way. See T3. |
| M8 action results list what changed | User Steps (H4) | idea | A User Step could note what changed after an action ("notification 'Saved' appeared; button 'Save' disabled"). That gives the agent the effect without a second `describe()`. See T4. |
| M9 Storybook `stories-changed`, `stories-find-by-component` | **C11** (scenarios for a changed view) | **easier, more urgent** | A framework vendor has now shipped "changed file → affected tests" as an agent tool, in preview. C11 is the same thing for Vaadin views, and the route data it needs is small. |
| M9 Storybook `review-create` | Changed in this PR (H5) | confirms direction | Pushing a curated review page for the agent's changes is what `summary.md` and the Base Run diff already do. Nothing to add. |
| M10 Playwright 1.65 Java `normalize().toString()` | **C6** (apply `Did you mean`), Dramafinder Migration Recipe | **easier** (small) | A tool that converts plain Playwright Java tests can now ask Playwright for the canonical `getByRole` form of a locator, instead of parsing selectors. It is useful only if a recipe from plain Playwright to Unified is planned. None is. |
| M10 Playwright `required` in ARIA snapshots, Blink mode, screenshot-baseline fix | C15 (screenshot comparison) | none | These are refinements of features C15 would only wrap. |
| M10 deferred retries, M16 Cypress re-run optimization | **C13** (flaky check) | none | Retry scheduling belongs to the Test Runner. Surefire covers reruns (N17). |
| M12 `playwright-mutation-gate` | **C3** (weak-test checks) | **prior art for a middle level; C3 level 2 still unshipped elsewhere** | The gate inverts one marked assertion per test. Here no marking is needed: the last `see` User Step of a scenario is known at run time, and on Browserless the inverted rerun costs milliseconds. Step-skip reruns (C3 level 2) go further than the gate: they test whether each *action* is needed. See T5. |
| M13 Applitools MCP (visual review through an agent) | **C15** | neutral | It confirms that the agent's job in visual testing is triage with human approval. C15 stays behind the Escape Hatch. |
| M14 Octomind, M17 Browser Use judge, Stagehand | **C4** | none | Cloud test generation or natural-language agents, with no Java and no portable test as output. C4's unique point (no browser needed, a portable Unified UI Test as output) stands. |
| M16 Cypress in agent sandboxes | **C7** (the loop, packaged) | **confirms** | "The agent tests its own changes before it hands them back" in a sandbox with no screen. Browserless already runs there with no browser to install. A short guide page saying so is cheap. See T6. |

**Redundant:** none. The closest is C9's browser half (M7), which is now available to agents outside a test.
