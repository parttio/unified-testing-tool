# How testing libraries document themselves for writers, reviewers and agents

Background research for the Unified API's documentation. It asks how established testing libraries organize and write their docs for three readers: (1) the developer who writes tests, (2) the person who reads and reviews tests written by a developer or an agent, and (3) the agent itself. It ends with recommendations for this repository's docs.

It doesn't repeat earlier notes. [web-framework-testing-landscape.md](web-framework-testing-landscape.md) covers the AI *features* (Playwright MCP and test agents, Cypress `cy.prompt`, which sites serve `llms.txt`), [readable-web-ui-tests.md](readable-web-ui-tests.md) covers how tests are made readable, and [page-objects-and-tasks.md](page-objects-and-tasks.md) covers test structure. This note is about the *docs*: what pages exist, in what order, for whom, and how they stay correct.

## Answer in short

1. **Nobody labels their docs "Diátaxis", but everyone separates the same four things.** A short *get started* path, task *guides*, a generated or semi-generated *API reference*, and a few *explanation* pages ("Guiding principles", "Core concepts", "Testing philosophy"). The order on every site is: get started → write → run → debug → reference → migrate/release notes. Explanations are kept short and placed first (Testing Library puts "Guiding Principles" inside Getting Started; Playwright's best-practices page opens with "Testing philosophy").
2. **Writers get one "best practices" page with *Bad/Good* pairs and one ordered locator rule.** Cypress has an Anti-Pattern/Best Practice pair per topic, AssertJ has "Avoiding incorrect usage" with *Bad*/*Good* blocks, Selenium splits "encouraged" and "discouraged" practices into separate pages, and Testing Library's query **priority list** is the single most-linked page in its docs. The rules are then enforced by a tool (ESLint plugin, SpotBugs/Sonar rule), and the docs say so.
3. **Reviewers get little explicit guidance, but the good docs teach *reading output*.** Cypress's first-test tutorial makes the test fail on purpose; every Cypress command page has a "Command Log" section that shows how the command looks in the runner; Selenium's exception messages link to a docs page per error with "Likely cause / Possible solutions"; Testing Library documents what a failing query prints. Only Selenium has a section written for reviewers of agent-written tests ("Reviewing agent-written tests", a five-step workflow), and only Cypress ships a *review* skill (`cypress-explain`) next to its *write* skill.
4. **Agents get the same docs in a different shape, plus a short rules list.** Markdown copies at `<page>.md`, `llms.txt`/`llms-full.txt`, and, new since the landscape note, **rules aimed at code generators written into the agent-facing files themselves**: Selenium's `llms.txt` opens with "Notes for tools generating Selenium code"; Cypress's `context7.json` carries ten rules; Dramafinder's `llms.txt` says "Do not decompile the jar". Selenium's `llms.txt` also leaves out legacy pages so agents don't learn from them.
5. **Code examples are kept correct by compiling them, not by review.** Selenium (six languages, a CI workflow each), AssertJ and JUnit include snippets from test sources that build and run. Playwright is the exception: its non-JS snippets are only syntax-checked. This repo already does the strong version.
6. **Playwright's Java docs are a filtered copy of the JS docs, and lose the advice.** The same Markdown sources are filtered by `* langs:` markers. The Java sidebar has no "Best Practices", no "Migration" section and no test agents; JS has all three. A Java tester gets the API and the guides but not the opinions.
7. **Change is communicated next to the API.** Playwright prints "Added in: v1.x" on every method; Cypress command pages end with a "History" table; JUnit has an "API Evolution" page that defines `EXPERIMENTAL`/`MAINTAINED`/`STABLE`/`DEPRECATED`/`INTERNAL`. Migration is a guide plus a tool: AssertJ points to OpenRewrite recipes first.

### What the order says

- **Diátaxis is implicit everywhere and explicit nowhere.** A search of all checked repos for "diataxis" found nothing. Yet each separates tutorial (Cypress "Your First Test", Cucumber "10-minute tutorial"), how-to (Playwright "Guides", Vaadin "Building apps"), reference (generated API pages) and explanation (Testing Library "Guiding Principles", Cucumber "BDD", Cypress "Core concepts", JUnit "Definitions").
- **Explanation is short and early.** Testing Library's "Guiding Principles" is 25 lines and the second page of Getting Started ([`guiding-principles.mdx`](https://github.com/testing-library/testing-library-docs/blob/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/guiding-principles.mdx)). Playwright's best-practices page opens with "Testing philosophy: Test user-visible behavior" ([`best-practices-js.md` L10–16](https://github.com/microsoft/playwright/blob/28c4b2e0ad892723c17c0b8d280207c1da670998/docs/src/best-practices-js.md#L10-L16)).
- **Debugging is its own top-level section.** Cypress: "Debug & troubleshoot" with debugging, common errors, FAQ and troubleshooting ([`docs/app/debug/`](https://github.com/cypress-io/cypress-documentation/tree/683828738ef3cd4c2e4836855535e9c12fcab6b9/docs/app/debug)). Selenium: "Troubleshooting" with one page per error and logging ([`webdriver/troubleshooting/`](https://github.com/SeleniumHQ/seleniumhq.github.io/tree/1a01796d14b610e595f67b89f43b42566d5465f9/website_and_docs/content/documentation/webdriver/troubleshooting)). Dramafinder: "Debugging failed tests". Vaadin: "Debug a Failing Browserless Test".
- **AI has its own section, next to the practices.** Cypress "Work with AI" sits between "Run tests" and "Configure"; Selenium "AI Agents" (weight 11) sits right before "Test Practices" (weight 12).
- **Legacy material is kept but fenced off.** Selenium has a "Legacy" section near the end, and its `llms.txt` lists it only under "Optional" with "Do not use it as a basis for new code" ([`layouts/index.llms.txt`](https://github.com/SeleniumHQ/seleniumhq.github.io/blob/1a01796d14b610e595f67b89f43b42566d5465f9/website_and_docs/layouts/index.llms.txt)).

### Playwright: how the Java docs differ

- **One source, filtered per language.** All languages are written in `docs/src/*.md`; sections carry `* langs: js` or `* langs: csharp, java, python` and the site generator keeps only the current language ([`debug.md` L6–7, L109–110](https://github.com/microsoft/playwright/blob/28c4b2e0ad892723c17c0b8d280207c1da670998/docs/src/debug.md#L6-L7); [`trace-viewer-intro-java-python.md` L63–64](https://github.com/microsoft/playwright/blob/28c4b2e0ad892723c17c0b8d280207c1da670998/docs/src/trace-viewer-intro-java-python.md#L63-L64); `filterForLanguage` in [`playwright.dev/src/generator.js` L82](https://github.com/microsoft/playwright.dev/blob/450154811efd75a43753df69d92f8e6283613c41/src/generator.js#L82)). Whole pages are per language by file name (`intro-java.md`, `writing-tests-java.md`).
- **The opinions are JS-only.** `best-practices` exists only as `best-practices-js.md` and is listed only in the JS sidebar ([`nodejs/sidebars.js` L55](https://github.com/microsoft/playwright.dev/blob/450154811efd75a43753df69d92f8e6283613c41/nodejs/sidebars.js#L55)); the Java sidebar has no best-practices page, no "Migration" category and no test agents ([`java/sidebars.js`](https://github.com/microsoft/playwright.dev/blob/450154811efd75a43753df69d92f8e6283613c41/java/sidebars.js)). Java gets the locator advice only through the "Quick Guide" on the Locators page, which lists the `getBy*` methods in order ([`locators.md` L11–20](https://github.com/microsoft/playwright/blob/28c4b2e0ad892723c17c0b8d280207c1da670998/docs/src/locators.md#L11-L20)).
- **Java adds runner pages instead.** "Test Runners" and "JUnit" are in Java's Getting Started, because Java has no Playwright Test runner.
- **Java's "Writing tests" is short.** Introduction, Assertions, Locators, Test Isolation, What's Next: about 100 lines ([`writing-tests-java.md`](https://github.com/microsoft/playwright/blob/28c4b2e0ad892723c17c0b8d280207c1da670998/docs/src/writing-tests-java.md)).

## 4. Guidance for reading and reviewing tests

### Reading output

- **How each command looks in the run.** Every Cypress command page has a "Command Log" section: the code, then a screenshot of how the runner shows it, then what the console prints when you click it ([`api/commands/get.mdx` L455–476](https://github.com/cypress-io/cypress-documentation/blob/683828738ef3cd4c2e4836855535e9c12fcab6b9/docs/api/commands/get.mdx#L455-L476)). The same page has "Rules": what the command retries and when it can time out (L434–453).
- **What a failure prints.** Testing Library's debugging page starts with "Automatic Logging": a failed query prints the DOM, shown verbatim, with the settings that shorten it ([`api-debugging.mdx` L6–40](https://github.com/testing-library/testing-library-docs/blob/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/dom-testing-library/api-debugging.mdx#L6-L40)). AssertJ shows the exact failure message next to each feature, for example `[check Frodo's age] expected:<100> but was:<33>` ([`assertj-core-assertions-guide.adoc` L137–155](https://github.com/assertj/doc/blob/2c79a20d365875998c400a0256ec1f67c21b6e6b/src/docs/asciidoc/user-guide/assertj-core-assertions-guide.adoc#L137-L155)).
- **From the error to its page.** Every Selenium exception message ends with "For documentation on this error, please visit: …/troubleshooting/errors#<exception>" ([`WebDriverException.java` L32–33, L80–81](https://github.com/SeleniumHQ/selenium/blob/095080829660c9fe263ea5bf545614000007e740/java/src/org/openqa/selenium/WebDriverException.java#L32-L33)). Each error on that page has "Likely Cause" and "Possible Solutions" ([`errors/_index.en.md` L75–92](https://github.com/SeleniumHQ/seleniumhq.github.io/blob/1a01796d14b610e595f67b89f43b42566d5465f9/website_and_docs/content/documentation/webdriver/troubleshooting/errors/_index.en.md#L75-L92)).
- **Tips for reading the evidence.** Vaadin's "Debug a Failing Browserless Test" ends with "Tips for Reading the Tree": look for what's missing, compare property values, watch for unexpected components ([`debug-tests.adoc` L124–131](https://github.com/vaadin/docs/blob/de63380263937bf5dce1705d30ce73077be12f71/articles/building-apps/testing/browserless/debug-tests.adoc#L124-L131)). Dramafinder's debugging page tables the files of its failure report and says which to open first ([`debugging.md` L3–19](https://github.com/parttio/dramafinder/blob/f0d56b9551aba8b5320267fb719dc15dbf146367/docs/guide/debugging.md#L3-L19)).

### Reviewing, and reviewing agent-written tests

- **Selenium** has the only reviewer section found: "Reviewing agent-written tests". "Review the diff for the patterns above, the way you would review a new starter's"; "Do not accept a sleep or a longer timeout as the fix for a flaky test"; and a five-step workflow: review the locators before any test is written, run that one test, "Run the test a few times before you believe it", review the diff ([`ai_agents/_index.en.md` L377–397](https://github.com/SeleniumHQ/seleniumhq.github.io/blob/1a01796d14b610e595f67b89f43b42566d5465f9/website_and_docs/content/documentation/ai_agents/_index.en.md#L377-L397)). A companion page lists each outdated pattern with its replacement ([`outdated_patterns.en.md`](https://github.com/SeleniumHQ/seleniumhq.github.io/blob/1a01796d14b610e595f67b89f43b42566d5465f9/website_and_docs/content/documentation/ai_agents/outdated_patterns.en.md)).
- **Cypress** splits writing and reviewing into two skills. `cypress-author` writes; `cypress-explain` "identifies intent, structure, Cypress mechanics, and hidden dependencies", flags "Brittle selectors, timing assumptions, unnecessary waits, UI coupling, and missing assertions", and "flags and corrects misleading or incorrect test titles" ([`ai-skills.mdx` L93–116](https://github.com/cypress-io/cypress-documentation/blob/683828738ef3cd4c2e4836855535e9c12fcab6b9/docs/app/ai/ai-skills.mdx#L93-L116)). The page gives review prompts, e.g. "Flag any tests that are likely to be flaky, over-coupled to implementation details, or missing meaningful assertions" (L389).
- **Vaadin** gives the rule for a failing story: "Decide which before you change anything, and don't weaken the story to make the test pass" ([`write-user-stories.adoc` L234](https://github.com/vaadin/docs/blob/de63380263937bf5dce1705d30ce73077be12f71/articles/building-apps/testing/browserless/write-user-stories.adoc#L234)). That is the key rule for an agent fixing a test.
- Nobody else (Playwright, Testing Library, JUnit, AssertJ) has a review checklist. Their review aid is the best-practices page read in reverse.

## What this means for the Unified API's docs

### What the repo already does well

Measured against the libraries above, this repo is already ahead on several points. Keep them:

- **Compiled, run examples.** Guide snippets are included with `--8<--` from `unified-test-demo` tests that run in CI on every Testing Tool, or from `GuideExamples`, which CI compiles ([docs/guide/index.md](../guide/index.md)). This is the Selenium/AssertJ/JUnit standard, stronger than Playwright's syntax check for Java.
- **Agent docs.** `llms.txt`, `llms-full.txt`, a Markdown copy of every page ([scripts/llms_txt.py](../../scripts/llms_txt.py)); the API reference inside the jar, as Dramafinder does; a `write-unified-ui-tests` skill installed by a recipe and pointed to from `AGENTS.md`; spec/ADR/release notes in llms.txt's "Optional" section.
- **Reports documented by reader.** [reports-and-failures.md](../guide/reports-and-failures.md) opens with a table of outputs and who each is for ("the reviewer", "agents and CI tooling"). No other library does this. The failure message is documented line by line, with Near Misses and *Did you mean*.
- **Rules enforced by a tool, documented with the rule.** [style-rules.md](../guide/style-rules.md) has a Rule / Fails when / Fix table, the exact failure output, `FreezingArchRule` for existing suites, and "What the rules don't check".
- **Migration as guide plus tool,** like AssertJ: OpenRewrite recipes first, the `resolve-migration-markers` skill second, with an evaluation of the skill.
- **Explanation kept separate.** The guide shows how; the [spec](../spec/README.md) says what is guaranteed and why; [GLOSSARY.md](../../GLOSSARY.md) plays JUnit's "Definitions" role.
- **Locator priority in the user's terms:** "By what the user sees (prefer these)" before "By technical attributes (fallback)" in [finding-components.md](../guide/finding-components.md), plus a cheat sheet.

### Recommendations, in priority order

1. **Add a page for the reviewer: "Reviewing a Unified UI Test"** (new `docs/guide/reviewing-tests.md`, in the nav right after "Reading reports and failures"). Today the reviewer's material is spread over [reports-and-failures.md](../guide/reports-and-failures.md) (summary.md, "Scenarios without a check", "Changed in this PR"), [structuring-a-scenario.md](../guide/structuring-a-scenario.md) and [style-rules.md](../guide/style-rules.md). Gather it into a checklist, as Selenium does for agent-written tests (§4): the `@DisplayName` states the scenario asked for; `user-steps.txt` tells that scenario, with a `see` line for every outcome; the run summary lists no "scenario without a check"; lookups use what the user sees; no getter plus `assertEquals`; no Escape Hatch without `@RequiresTestingTool`; it passed on Browserless *and* a browser, more than once; a fix didn't raise the timeout or weaken a check (Vaadin's "don't weaken the story", Selenium's "Do not accept a sleep or a longer timeout"). Add a short "Reviewing a test an agent wrote" section with Selenium's workflow adapted to the skill's steps.
2. **Give agents a review mode, not only a write mode.** Cypress ships `cypress-explain` next to `cypress-author` (§4). Either add a "Review a test" section to [`write-unified-ui-tests/SKILL.md`](../../unified-test-rewrite/src/main/resources/META-INF/unified/skills/write-unified-ui-tests/SKILL.md) that applies the checklist from recommendation 1, or add a second skill `review-unified-ui-tests` installed by the same recipe. The skill's "Prove it" step already reads `user-steps.txt` against the request; the review mode should do the same for a test it didn't write, and should flag misleading `@DisplayName`s, as `cypress-explain` does for titles.
3. **Put rules for code generators into `llms.txt` itself.** Selenium's `llms.txt` opens with "Notes for tools generating code" and Cypress's `context7.json` carries ten rules (§5). Extend the intro written by [scripts/llms_txt.py](../../scripts/llms_txt.py) (the `lines = [...]` block) with five to eight rules taken from the "Rules of thumb" in [docs/guide/index.md](../guide/index.md) and the skill's canonical forms: import `assertThat` from `UnifiedAssertions`; find by label or text, test id last; never `Thread.sleep` or a Testing Tool's waits; never name a Testing Tool unless `@RequiresTestingTool`; read `META-INF/unified/api-reference.md` from the jar instead of decompiling; and the patterns migrants bring (TestBench `$(..)`, Playwright `page.locator("css")`, Browserless `test(..)`). Name the skill's source URL there too. Keep the list in one place (for example a `docs/guide/rules.md` snippet) so `index.md`, the skill and `llms.txt` can't drift.
4. **Make the first test fail on purpose.** Cypress and Cucumber teach reading a failure before the green run (§2). Add "4. Break it" to [getting-started.md](../guide/getting-started.md): change the label in the test to `"E-mail"`, run, and show the real `UnifiedAssertionError` (Near Miss, *Did you mean*) and the test's `user-steps.txt`; the demo already has this case in `GuideExamples.changesTheEmail`, so the output can be included rather than retyped. This puts the reader-2 skill (reading output) on the onboarding path.
5. **Add a "Common mistakes" page with Bad/Good pairs.** Cypress, AssertJ, Selenium's "Outdated patterns" and Dramafinder's "Flaky tests" (§3) all have one. The repo has the rules (guide index "Rules of thumb", style rules, "What the rules don't check") but no page of *Bad*/*Good* code. New `docs/guide/common-mistakes.md`, each entry a pair and a link to the guide page or style rule that covers it: getter + `assertEquals`; `Thread.sleep`/tool waits; `all().get(0)` instead of a narrowing filter; a test id where a label exists; holding a value instead of the Wrapper; a test that ends on an action without a check; habits carried over from TestBench, Browserless and Dramafinder (links to the three migration pages). This page is also the input for recommendations 2 and 3.
6. **Show the User Step in the API reference.** Cypress gives every command a "Command Log" section; Dramafinder gives every method a one-line description (§7). The generated [api-reference.md](../../unified-test-api/src/main/resources/META-INF/unified/api-reference.md) lists signatures only, and nothing links back to the guide. Extend the generator to add, per action and check, the one-line Javadoc summary and the User Step wording it reports (e.g. `setValue(String)` → `fill text field “Name” with “…”`), and a "Guide:" link per Wrapper to its section in [components.md](../guide/components.md) or [grid.md](../guide/grid.md). A reviewer can then map a line of `user-steps.txt` back to the code, and an agent can predict what the report will say.
7. **Add a troubleshooting page keyed by failure, and link to it from the error.** Selenium's exceptions carry a link to a "Likely cause / Possible solutions" entry (§4). New `docs/guide/troubleshooting.md` with one entry per `Found` value of a `UnifiedAssertionError` (`none`, `2: …`, `1, but disabled`, a value seen while waiting), per style-rule failure, and for browser-only trouble (Playwright browser download, TestBench license, base URL). Consider adding a `Docs` line with the entry's URL to the failure message (spec chapter 12, "Failures"). Move the README's "Not in this first version" table into a "Known limitations by Testing Tool" section of that page, linked from the README, so it is versioned with the guide.
8. **Regroup the developer guide nav by reader task.** Thirteen flat pages today in [mkdocs.yml](../../mkdocs.yml). Group them as Cypress and Playwright do: *Get started* (getting-started) · *Write* (finding-components, components, grid, assertions-and-waiting, structuring-a-scenario, navigation-and-users, common-mistakes) · *Read and review* (reports-and-failures, reviewing-tests, troubleshooting) · *Run* (ci-setup, configuration) · *Extend* (tool-specific, custom-wrappers, style-rules) · *For agents*. Move the guide index's "For agents" section to its own page, as Cypress ("Work with AI") and Selenium ("AI Agents") do, covering the skill, the jar's API reference, `llms.txt`, `summary.json` and how to review what the agent did. Pull the three migration pages and `comparison.md` under one "Coming from another tool" group.
9. **Add a recipes page later.** Dramafinder, Testing Library and Cypress have one (§9). A `docs/guide/recipes.md` of whole scenarios (fill and save a form, edit a grid row in a dialog, confirm a destructive action, two users on one view) taken from demo tests would help writers and give agents complete patterns. Lower priority: the component pages already cover most single actions.
10. **Plan stability markers before `spec-v1`.** The repo marks *(unreleased)* by hand. When the API leaves alpha, follow JUnit's "API Evolution" (§8): a status per type or member (experimental, stable, deprecated), shown in the generated API reference, plus a "since" version per member like Playwright's "Added in". Until then the current scheme is enough.
