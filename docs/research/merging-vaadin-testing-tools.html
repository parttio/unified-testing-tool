Merging Vaadin's testing tools

Should TestBench, Browserless Test and Dramafinder become one library? How much of their code repeats the same work, and what would one official testing API look like?

testbench 4e1c923 browserless-test f69a50d dramafinder f3c30db unified-testing-tool fdbe120 flow-components d1a42ad flow 32e7f0a
Recommendation opinion

Merge in stages into one official product with one API and two kinds of runtime, not one jar. Each component gets one wrapper interface with exactly two behaviour implementations: one for the server-side component tree (Browserless) and one for the DOM, shared by Playwright and Selenium. That component knowledge lives in flow-components, released with the component. Delete TestBench UI Unit now. Keep Selenium as a commercial driver.

  1. 01

    There are five component-wrapper libraries for one component set, not three tools. About 63,000 lines of main code do nothing but drive Vaadin components. 43 components are wrapped by all three tools, and a combo box has four names for the same act.

  2. 02

    The largest duplication is accidental and already decided. TestBench UI Unit is a fork of Browserless: 60% of its code lines and 89% of its test lines appear unchanged there. It is deprecated, yet both repos still take the same fixes, such as the shortcut-filter fix on 2026-11-13 (testbench@0adbfbb, browserless-test@4930397).

  3. 03

    The two browser libraries duplicate each other, mostly by accident. TestBench and Dramafinder drive the same web components; only the protocol differs. Both restate every tag, embed the same server-idle wait script, and call Grid's private JavaScript API from separate copies.

  4. 04

    The Unified API proves one API over three runtimes works, but adds a fifth layer. Its adapters sit on top of the tools' own wrappers, and its driver interface names specific components (GridAccess, LoginAccess).

UI Unit is a fork of Browserless

Every one of UI Unit's 62 testers has a same-named Browserless tester. Fix: delete UI Unit; the MigrateUIUnitToBrowserless recipe moves users.

The round-trip wait, three times

The script that polls Vaadin.Flow.clients[..].isActive() exists in TestBench, Dramafinder and the Unified API. Fix: one public "client is idle" API in Flow.

Grid's private API, four copies

_scrollToFlatIndex, _flatSize, _getColumns are called from TestBench, Dramafinder and both Unified browser adapters. Fix: a supported test hook on <vaadin-grid>.

Tags restated

Flow's @Tag already names each element. TestBench repeats it 86 times, Dramafinder 57 times. Fix: read @Tag, as the Unified API does.

Two browser element libraries

49 components are wrapped by both TestBench and Dramafinder, against the same DOM, with different vocabularies.

Unified adapters repeat each other

Spring test login, test runner glue, failure evidence

Each tool has its own login endpoint, JUnit extension, screenshot or tree dump, and (two of them) agent report.

Conceptual · necessarily different
Component actions, server versus browser

A Browserless tester sets the value so the event reports isFromClient(); a browser element types and clicks. One side has a component tree and no DOM, the other a DOM and no server objects. This is the one split a merged product keeps.

Lookups

The traversal differs, but the vocabulary (withLabel, withText, withId) need not. The Unified API already has one filter set over all three.

Waiting

In the JVM an action is synchronous; in a browser it waits for actionability and the round trip. Same guarantee, implemented per runtime.

Users and sessions

Browserless switches thread-locals per simulated user; browsers need separate contexts and a real login.

opinion About a third of the 63,000 lines is accidental and a merged product removes it outright: UI Unit, one of the two browser element libraries, and most of the Unified adapters' per-component code.

Should they merge or move?

Five options, ranked opinion

Constraints any option must meet: Browserless already targets exactly one Flow version; TestBench is commercial and licence-checked while the others are Apache-2.0; existing suites in all three APIs must keep compiling during a transition.

1

Shared component model in flow-components, pluggable drivers

One wrapper per component, one server and one DOM behaviour, thin Browserless / Playwright / Selenium drivers. Removes most duplication: five wrapper libraries become one API and two behaviour sets. Medium migration cost, automated by existing recipes. 3–4 quarters.

End state
2

One monorepo, separate artifacts

One build, CI, BOM and release. Removes no code by itself, but makes deleting UI Unit and sharing the wait, tag and Spring code a normal refactor. No user migration.

Status quo with the Unified layer on top

Available now and costs users nothing, but adds a fifth wrapper library. Every component change lands in up to four places.

  1. Component knowledge exists once per runtime family. Playwright and Selenium contain no component code.
  2. Drivers are thin: start, find nodes, run a user gesture, run a script, wait.
  3. The driver interface names no component. An add-on adds a component without touching it.
  4. Browser behaviour calls public test hooks on the web component, not private fields.
  5. Everything versions with Vaadin, as Browserless already does.

Driver interface

public interface Driver {
  Runtime runtime();          // SERVER or DOM
  Set<Capability> capabilities();
  Session open(DriverContext ctx);
}
public interface Session extends AutoCloseable {
  List<Node> find(NodeQuery q); // no component types
  void navigate(String path);
  void awaitIdle();           // one Flow API
  Session openAsUser(String user, String... roles);
  <T> Optional<T> unwrap(Class<T> type); // escape hatch
}

Most of the Unified API's design decisions carry over: filters that follow component type, wrappers as interfaces in the component's jar, a test-runner-neutral lifecycle, the Findable View and the migration recipes. The design departs from it in three places: drivers per runtime instead of adapters per tool, no per-component *Access interfaces in the driver SPI, and drivers that sit on the runtime instead of on another wrapper library.

    Free

    The API, the Browserless and Playwright drivers, JUnit / Spring / Quarkus integration, migration recipes, agent skills.

    Commercial (TestBench)

    Selenium driver with Grid, cloud vendors and real Safari; visual comparison on any driver; the k6 kit that turns UI tests into load tests; team reporting.
