Answer in short

  1. Browserless or real browser? Both, in layers, almost everywhere. Every framework checked recommends a fast layer without a real browser for most tests, plus a thin layer of real-browser end-to-end (E2E) tests for critical flows. The fast layer is one of two kinds. JavaScript frameworks (Angular, Vue, Svelte, React via Testing Library) run component tests in Node with an emulated DOM (jsdom or happy-dom). Server-side frameworks test on the server with no DOM at all: Vaadin Browserless, Phoenix LiveViewTest, Spring MockMvc, Django's test client, Wicket's WicketTester, Blazor's bUnit. A third option is growing: component tests in a real browser through Vitest browser mode. Angular supports it, Vaadin's React-view guide uses it, and Svelte uses it through Storybook. For E2E, Playwright is the default or first-listed choice in Angular, Vue, Svelte, Next.js, Blazor and Pest/Laravel. Rails and Django still default to Selenium. Vaadin's own E2E tool, TestBench, is Selenium-based and commercial.
  2. Audience: developers first. The official guides of every framework are written for developers. Business-readable tests show up in three forms. (a) Cucumber/Gherkin, which says outright that it closes "the gap between business people and technical people". (b) Plain Java or PHP written as user stories. Vaadin's Browserless docs ask for tests that "a product owner can read … aloud". (c) Since 2025, natural-language steps and specs: Cypress cy.prompt names "product owners, QA, and developers" as authors, and Playwright's planner agent writes Markdown test plans. Recorders (Playwright codegen, Cypress Studio, Selenium IDE, Vaadin Copilot) are the low-code way in. All of them produce ordinary code that a developer then owns.
  3. Official AI features, as of 2026-11: Playwright has the most. It ships an MCP server and playwright-cli (bundled since 1.62), the planner/generator/healer test agents (1.56, JS only), "Copy prompt" on failures (1.51), a trace CLI for agents and "video receipts" (1.59), and an 'ai' snapshot mode with getByRef (1.64). Cypress has cy.prompt (natural language with self-healing, beta since 15.13), Studio AI, agent skills, cypress tap, and a Cloud MCP (generally available 2026-05-20). Selenium ships no AI tools of its own. Instead it has an "AI Agents" docs page that tells agents what not to write, plus an llms.txt. On the framework side, Angular (a CLI MCP server with run_target for tests, skills, llms.txt, rules files), Next.js (a dev-server MCP, docs bundled in node_modules, a managed AGENTS.md), Svelte (MCP, skills, subagents), Laravel (Boost: MCP, guidelines, skills) and Vaadin (a docs MCP server, skills, a dev-loop CLI for agents, Copilot test generation) all give agents context and a run loop. None of the frameworks ships its own test-writing agent. They lean on Playwright's or Cypress's.
  4. New patterns because of agents: (a) the accessibility tree as the agent's view of the page: Playwright MCP's snapshots, Playwright's 'ai' aria snapshot with element refs, boxes "useful for AI consumption", and the WebDriver BiDi spec's accessibility locator; (b) role and name locators as the shared language between humans, codegen and agents; (c) CLI plus skills instead of MCP for coding agents, now recommended by Playwright itself because it uses fewer tokens; (d) docs written for agents: llms.txt, Markdown copies of doc pages, docs bundled with the package, AGENTS.md blocks managed by the framework; (e) agent-readable failure output: a trace CLI, "Copy prompt", Cloud MCP, --json output, browser console forwarded to the terminal; (f) self-healing, either as a reviewed code change (Playwright healer) or at runtime (cy.prompt). Most framework repos now carry an AGENTS.md or CLAUDE.md for their own contributors, and Next.js, Phoenix and Laravel Boost write one into users' apps.
  5. How humans read tests: by names and steps, by reports and traces, and more and more through AI summaries. Playwright's trace viewer and HTML report are the reference. Cypress has the Command Log, Test Replay and AI "Test Intent Summaries". For review, the tools stress that AI output is plain code that goes through normal review (Cypress: "PR review friendly"; Playwright: "simple, auditable structure"). Selenium gives a checklist for reviewing agent-written tests. Playwright 1.59 adds annotated "receipt" videos so a human can check what an agent did.

Inferences (our reasoning, not sourced fact)

  • The consensus is a test pyramid with a browserless base. Server-side frameworks (Vaadin, Spring, Rails, Django, Phoenix, Wicket, Blazor) all say: most tests without a browser, a few in a browser. Rails went further and stopped generating browser tests by default. Vaadin's guidance (B1–B3) is in line with this.
  • "Browserless" means two different things. For JS frameworks it means an emulated DOM (jsdom, happy-dom), where the same DOM-level locators still work. For server-side frameworks it means no DOM at all: the test reads the server's component tree. The Unified API has to bridge exactly this gap. Locating by label, text and accessible name works on both sides. CSS does not.
  • Real-browser component tests are the newer middle layer (Vitest browser mode, Cypress component testing, Storybook). They cut into the "emulated DOM" layer in JS land. They don't apply to Flow, where rendering needs the server.
  • The closest prior art to the Unified API is Angular CDK component harnesses (A3–A4). They give one test API that runs on a unit environment and on a WebDriver environment, with an SPI for more environments. That is the same idea as a Wrapper running on several Testing Tools, one level below.

Inferences

  • No framework targets non-developers with its own test API. The audiences are developers (component tests), developers and QA (E2E), and business readers through a layer on top: Gherkin, user-story page objects, Markdown plans or natural-language prompts.
  • Natural language is replacing Gherkin as the "business-readable" entry point in AI tools. cy.prompt steps and Playwright's Markdown specs play the role Gherkin played, but without step definitions to maintain. That gain comes with a cost: the result is not deterministic until it is turned into code (§3).
  • Cucumber's "declarative, no 'click a button'" advice (AU4) and Vaadin's user-story layers (AU5) say the same thing. The readable layer should name intents, and the locators belong one layer down. This is relevant to #193.

Inferences

  • Who does what. Test tools (Playwright, Cypress) build the agents that write, run and heal tests. Frameworks build what makes agents correct: current docs, best-practice rules, and a fast "did my change work" loop. Vaadin follows the framework pattern, and its Copilot test generation is the exception (see the Copilot note).
  • Healing comes in two forms. Playwright's healer changes the test source, and the change is reviewed like any other code. cy.prompt "continuous self-healing" changes behaviour at runtime, with a "Self-healed" tag in the Command Log as the audit trail. The first form fits a project that values deterministic, reviewable tests.
  • Java is behind. Playwright's test agents are JS-only (AI2). The Java tooling for agents is MCP/CLI-based browser control plus project skills, such as Dramafinder's (AI21) and Vaadin's (AI20). We found no official AI tooling in TestBench beyond Copilot's generator.

Inferences

  • The accessibility tree has become the shared view of the page for humans, test code and agents. Agents see the page as an ARIA snapshot (AG1, AI3). Codegen and the generator agent emit getByRole(role, { name }) (AG2). BiDi now standardises an accessibility locator (AG5). Tests written in role-and-name terms are therefore the ones an agent can both write (it reads roles and names) and repair (the healer re-locates "equivalent elements").
  • Test ids remain a respected minority view. Cypress, Selenium and Phoenix's agent rules prefer stable ids (AG4). Their argument is that ids are isolated from copy changes. The role-based side argues that ids prove nothing about what the user sees.
  • "Docs for agents" is now a standard deliverable. Most framework sites serve llms.txt. Several ship MCP servers. Next.js, Phoenix and Laravel manage blocks in the user's AGENTS.md. Selenium wrote a page whose only purpose is to correct what models learned from old blog posts.
  • Fewer tokens wins. Playwright now steers coding agents from MCP to CLI plus skills (AI4), and Next.js reports better agent results from bundled docs plus AGENTS.md than from skills (its claim, from a Vercel blog post we did not verify). Expect compact, text-first outputs: snapshot files, find, JSON, exit codes.

Inferences

  • Humans read tests through three channels: the source (names, steps, intent-level helpers), the run record (trace, Command Log, report, video) and, more and more, AI summaries of both. For AI-written tests, the run record and a clean diff matter more, because the reviewer did not write the steps.
  • Every vendor stresses that AI output is ordinary code going through ordinary review. None of them offers a separate "AI test" format. Runtime self-healing is the exception, and it adds visible tags so a human can audit it.

What this means for this repo (inferences)

Our reasoning, not sourced fact

All of this section is our reasoning. It is not sourced fact.

  1. The Unified API's locator style fits the agent era. The query shape find(Wrapper.class).withLabel/withAccessibleName/withText(...), with withTestId/withId as fallbacks (spec 04, ADR 0001), is Playwright's getByRole(role, { name }) with the Wrapper type in place of the role. It follows the same order as Testing Library (AG3), and the same order Playwright's generator and codegen emit (AG2). So an agent that reads an ARIA snapshot (textbox "Name") has a direct mapping to find(UnifiedTextField.class).withLabel("Name"). The same mapping would let a Migration Recipe or agent skill convert agent-generated Playwright tests. One open point: Cypress-, Selenium- and Phoenix-style id-first tests (AG4) map only to the fallback filters.
  2. Angular CDK harnesses are the nearest prior art (A3–A4): one component API on a no-browser environment and on WebDriver, with an SPI for more environments. Worth a look for the adapter SPI and Wrapper authoring docs, and worth citing in an ADR as precedent.
  3. The Browserless-first stance matches the field. Vaadin, Spring, Rails, Django, Blazor and Phoenix all recommend a fast base and a thin browser layer. No other framework we checked lets the same test run in either layer by choice per run. That is the Unified API's distinct value, and it is worth stating plainly in the README.
  4. Agents need a text view of the page. Browserless already writes a text component tree on failure (spec 09). Playwright and Selenium only write a screenshot. A tool-neutral text snapshot in role-and-name terms, on every Testing Tool, would give an agent (and a human) the same failure view whatever the Testing Tool. That is the "agent-readable output" pattern (AG12, AI7, AI8).
  5. Ship docs for agents with the jar, as Dramafinder does (AI21): a START-HERE.md, the API reference and the migration guides under META-INF. Also consider an llms.txt for the docs site and a short AGENTS.md. This follows the pattern across the field (AG6–AG11), and ADR 0004 already plans an agent skill for migration.
  6. Healing should produce a diff, not a runtime guess. The lazy, re-finding Wrapper already avoids stale references. If the project ever helps with broken locators, Playwright's healer model (propose a code patch, rerun, skip if the feature is broken) fits a deterministic, reviewed test suite better than cy.prompt's runtime healing.
  7. Readable tests sit one layer above locators. Cucumber's declarative style, Vaadin's user-story layers and Playwright's Markdown specs all keep intents in the readable layer and locators below it. This supports #193 and the step-report idea in #195.

Open questions

  • Should the Unified API offer a tool-neutral accessibility snapshot (read and assert), like Playwright's toMatchAriaSnapshot? Can Browserless compute roles and names close enough to the browser's to make that portable?
  • Does Playwright's healer or generator work on Java Playwright, or on Dramafinder or Unified tests, through MCP alone? The agent definitions are JS-only (AI2). This was not tested.
  • Does the Vaadin MCP server know about Browserless locators, and will it know about the Unified API? Vaadin Skills list no testing skill (AI19).
  • Next.js's claim that bundled docs plus AGENTS.md beat skills comes from a Vercel blog post and an evals page. Neither was verified.
  • Since which Rails version do scaffolds skip system tests? The guide doesn't say (RA2).
