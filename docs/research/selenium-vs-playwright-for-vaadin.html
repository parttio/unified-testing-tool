Selenium or Playwright for Vaadin browser tests

Vaadin has two Java browser-test libraries: the official TestBench, built on Selenium WebDriver, and the community Dramafinder, built on Playwright. This page compares the two foundations and asks whether Vaadin should ship an official Playwright wrapper.

Read against vaadin/testbench@11908ed (Selenium 4.53.0), parttio/dramafinder@bce0654 (Playwright Java 1.63.0) and unified-testing-tool@7916497. Facts are cited in the full Markdown note by ID (P1, T3…). opinion marks reasoning.

Recommendation: yes, support Playwright officially, as a second backend under one Vaadin test API. opinion

Bring Dramafinder under Vaadin's support now, keep TestBench on Selenium fully supported, and converge later on one API with Selenium, Playwright and Browserless backends. Settle what stays in the paid tier before announcing anything.

Answer in short

  1. Playwright's general advantages are real and documented. Every action waits until the element is visible, stable, enabled and receives events. Locators reach into open shadow roots and are strict, so a double match fails instead of taking the first. It adds a trace viewer, Java codegen, network mocking and cheap isolated browser contexts. Apache-2.0.
  2. For Vaadin apps the gap is smaller than it looks. Playwright's waiting knows nothing about Vaadin's server round trip. Dramafinder (AutoWait) and TestBench (waitForVaadin) close it the same way, by polling window.Vaadin.Flow.clients. TestBench's query script also searches shadow DOM already.
  3. Selenium wins on standards, reach and Vaadin's install base. W3C WebDriver Recommendation, WebDriver BiDi written with browser vendors, real branded Safari, Selenium Grid and cloud vendors, Appium for mobile, and TestBench's screenshot comparison.
  4. Playwright Java is a second-tier binding. Not thread safe; JUnit fixtures and the Selenium Grid connection are both marked experimental.
  5. Licensing is the business question. TestBench's browser testing needs a Pro subscription; Dramafinder is free. A free official Playwright option changes what Pro buys.

Where each one wins

Playwright / Dramafinder

  • Actionability auto-wait before every action (P1)
  • Shadow-piercing, strict locators; no silent first() (P2, D3)
  • Trace viewer: DOM, network and source per action (P3)
  • Codegen that writes Java with role and label locators (P4)
  • Network routing, mocking and HAR replay (P5)
  • Browser contexts that are cheap and fully isolated (P6)
  • Apache-2.0 at both layers; browser builds pinned per release (P9, P12, D1)
  • Default E2E tool for most modern web frameworks (landscape)

Selenium / TestBench

  • W3C standard since 2018; BiDi is the vendors' shared successor (S1–S3)
  • Real branded browsers, Safari included (S7, P9)
  • Selenium Grid; TestBench @RunOnHub and Sauce Labs (S4, T5)
  • Real mobile devices through Appium (S8)
  • Screenshot comparison built in (T4, V3)
  • Reference Java binding, mature and thread-friendly
  • Backed by Vaadin, several maintained release lines (T7)
  • The existing customer suites

What it means for a Vaadin app opinion

Shadow DOM

Both wrappers already hide it for Vaadin components. Playwright helps when a test drops below the wrapper, for example a raw getByRole(..) against a third-party web component.

Flakiness

The Vaadin-specific kind, acting before the server answers, is handled the same way in both. Playwright adds general actionability waits and strict matching, so fewer flaky tests is a fair expectation but unmeasured.

Speed

Unproven here. Cheap contexts and one in-page wait script (vs polling from Java) make Playwright likely faster per test.

Debugging

The trace viewer is the clearest gain for a developer staring at a red CI run. TestBench has no equivalent.

Infrastructure

Teams on Selenium Grid, a cloud grid, real Safari or real mobile devices stay best served by Selenium.

Long-term stability

WebDriver is implemented by browser vendors. Playwright depends on patched browsers and one vendor's release train: reproducible, but frequent upgrades.

Should Vaadin ship an official Playwright wrapper?

A · Keep Selenium only

TestBench stays the only official tool; Dramafinder stays community.

Cheapest. Leaves Vaadin out of step with where other frameworks point users.
B · Wrapper beside TestBench

"TestBench for Playwright": a second element library with its own API.

Two libraries to keep in step with every component, for good (~24k lines in Dramafinder).
C · Backend under a common API

One Vaadin test API, Selenium or Playwright chosen per run.

Playwright-only features (trace, routing) need deciding what to lift into the API.
B → C · Recommended

Adopt Dramafinder now; converge it and TestBench towards one API with two backends.

Fast to start, avoids a permanent second API.

Benefits

  • Meets users where the field is going: Playwright is the first-listed or default E2E tool in Angular, Vue, Svelte, Next.js, Blazor and Laravel, and has the most agent tooling.
  • Trace viewer, codegen and network mocking on Vaadin apps, with Vaadin-aware waiting.
  • Turns a single-maintainer add-on into something companies can depend on.
  • Some know-how is in-house: TestBench's load-test kit already uses Playwright 1.65, and Vaadin's docs mention it.

Costs and risks

  • Licensing and revenue: commercial competes with free Dramafinder; free removes a reason to buy Pro.
  • Microsoft's release train: new browsers every release; Java binding partly experimental.
  • Gaps for current users: grid and cloud, real Safari, mobile, screenshot comparison.
  • Migration cost for existing suites if Selenium is ever de-emphasised. Recipes help but leave Migration Markers.

This repo is a working prototype of option C

Unified UI Test→BrowserlessPlaywright · Dramafinder 2.2.1Selenium · TestBench 25.3

One test runs on any of the three, chosen per run with vaadin.testing.tool. Each browser adapter is only about 2,200–2,500 lines because it sits on the tool's own element library. Auto-Wait is a guarantee of the API: the Selenium adapter calls waitForVaadin, the Playwright adapter calls Dramafinder's AutoWait. Tool-only features go through an Escape Hatch and a declared Capability, so network interception and tracing stay Playwright-only today.

Recommended path opinion

Now

Keep TestBench Selenium fully supported. Co-maintain Dramafinder, run it in Vaadin's component CI and promise compatibility with each Vaadin release.

Next

Converge on one Vaadin test API with Selenium, Playwright and Browserless backends. Choose between TestBench's $(..) style and the Unified API's find(..) style.

Before announcing

Decide what stays in Pro: screenshot comparison, grid and cloud, load testing, migration tooling.

Throughout

Do not drop Selenium. The standard track, real branded browsers and existing customer suites keep it relevant.
